CRITICAL — WAF BLOCKING MODEL (read before any tool call):
The WAF does NOT typically answer with 403/406/501. It answers with HTTP 404.

Signature of an ASM/WAF block OR custom deny page (observe ALL of these together):
- Status: HTTP/2 404
- Title / body: French page "Erreur 404 - Oups." (HTML card + robot SVG)
- content-length: ~3821 (stable for the deny page)
- Headers almost always identical:
  x-frame-options: DENY
  x-xss-protection: 1; mode=block
  x-content-type-options: nosniff
  content-security-policy: default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'
  referrer-policy: no-referrer
  strict-transport-security: max-age=31536000; includeSubDomains
  pragma: no-cache / cache-control: no-store...
- wafw00f: clean request can differ from attack string (e.g. XSS) → same 404 façade used as block

IMPORTANT — 404 is AMBIGUOUS here. Do NOT conclude "path missing" from status alone.
Differentiate every response:
1) WAF/custom deny: HTML "Erreur 404 - Oups.", CL≈3821, headers above → treat as BLOCKED (policy/signature), not as discovery miss.
2) App transfer.sh response: body mentions "Easy file sharing" / DutchCoders / curl --upload-file examples (may still be status 404) → app reached; parse body for real behavior.
3) True empty/other: different CL, different title, JSON/error from app → note separately.

Never spam attack payloads. When testing WAF, use ONE controlled probe per class (XSS query, SQLi query, traversal) and compare body hash / title / CL to the deny page baseline.
